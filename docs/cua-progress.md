# CUA 结果记录与恢复

本专项指南为中文。CUA 使用已有 `memory.md`、Pi 会话、trace、图片归档和下载文件保存进度，不引入独立的业务验证引擎。操作流程见 [CUA skill](../.pi/skills/cua/SKILL.md)，持久目录见 [数据布局](task-workspace-layout.md)。

关键保存、导出或提交前，先在 Main 的 `agents/main/context/memory.md` 落盘操作意图、可重查的操作/回执标识、预期结果、核对方法及 `unknown` 进度，写明“恢复后先只读查证，不盲目重复本次输入”，等待写入成功再行动。这覆盖输入已送出、结果记忆尚未更新就硬崩溃的窗口。使用提示或 `clear_context` 描述中给出的实际绝对路径；普通 `write`/`edit` 的相对路径从项目目录开始。

结果后更新现有 Goal、Completed、Next 和约束，保留以下要点即可：

| 要点             | 记录内容                                                                                            |
| ---------------- | --------------------------------------------------------------------------------------------------- |
| Expected outcome | 用户要得到的结果；例如“订单已保存且可从状态页查询”                                                  |
| Evidence         | 实际文件路径、字节数/hash、`imageRef`、回执 ID 或可重查的状态页；只引用，不复制截图/base64/完整日志 |
| Check            | 哪些由工具或文件复读确认，哪些仍是模型根据画面的判断                                                |
| Progress         | `confirmed`：所列证据支持预期结果；`unknown`：尚未查证，或反馈缺失/冲突                             |
| Next             | 可执行的下一步和应避免重复的提交动作                                                                |

`dispatchStatus: sent` 只证明输入投递，`condition_met` 只证明指定 UI 条件。只有这些信号时，业务进度仍可为 `unknown`。文件存在不等于内容正确；需要时复读文件并核对内容/hash。视觉判断标明来源和局限，不伪装为机器检查。

重置上下文前先更新 memory，再调用 `clear_context`；普通压缩也读取同一份长期记忆。Pi 会话与完整消息继续保存，图片和已接受的下载文件随 Task 保留。重启不恢复旧浏览器页面、VM `state` 或原生动作凭据。

恢复时先读 memory 和证据，必要时查看 `agents/main/context/messages.json` 或会话/trace，再取得当前目标的新观察。对 `confirmed` 的步骤先核对持久证据及当前状态；对 `unknown`，优先按回执/操作标识只读查询业务结果。输入已经 `sent` 或投递状态为 `unknown` 时，不因超时、脚本重置或截图缺失而盲目重复提交；查不到结果也不能直接推断此前未执行。

完成仍由 Main 根据用户目标及证据判断；`finish_task` 的机械生命周期检查不代替业务验收。技能是模型执行约定，当前没有自动阻止一切重复业务操作的通用门禁。

回归见 [真实 Pi 进度恢复](../test/cua-progress-recovery-pi.test.js)：本地假模型驱动生产 Main/Pi、真实 Chromium、真实提交服务和文件核对，覆盖 confirmed/unknown 记忆的压缩与重启恢复，以及只有事前 intent 记忆、输入已 sent 但结果未记录时的 SIGKILL 恢复；新进程先只读查证，再确认结果，并以服务端提交次数验证没有重放。它不证明任意真实模型都能正确判断业务完成。
