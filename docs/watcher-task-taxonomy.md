# Watcher 任务分类与模板范围

本页按预期事件组织监控任务与参考模板，含未实现的扩展方向。当前运行范围见 [运行时参考](runtime-reference.md#长期目标接口与调度) 与 [参考模板](../.pi/skills/virtual-agent-authoring/templates/README.md)；[早期验证范围](watcher-template-verification.md) 不代表现行版本已验收。

Watcher 的目标是用代码持续观察，在出现值得处理的事实时交给模型。任务按“要发现什么变化”分为五类：程序运行、数值指标、资源版本、新增信息、实体状态。Session 归属、数据来源和触发方式单独描述，供各类任务组合使用。

## 五类监控任务

| 类别        | 要回答的问题                                   | 典型任务                                  | 可以复用的检查逻辑                               |
| ----------- | ---------------------------------------------- | ----------------------------------------- | ------------------------------------------------ |
| W1 程序运行 | 这项工作是否启动、推进、结束或出现异常？       | 训练、评测、构建、下载、批处理            | 运行身份、退出状态、进度标记、明确错误和停滞信号 |
| W2 数值指标 | 某项数值是否越界、突变或持续呈现某种趋势？     | loss、验证分数、显存、服务延迟、价格      | 阈值、变化幅度、连续命中、时间窗口和趋势         |
| W3 资源版本 | 已知资源是否生成、更新、删除或发生指定差异？   | checkpoint、报告、目录、配置、指定网页    | 存在性、版本号、指纹和选定内容差异               |
| W4 新增信息 | 信息流里是否出现了新的、与目标有关的条目？     | 新闻、RSS、论文、公告、帖子、新增披露记录 | 增量读取、条目去重、关键词和可选的相似度筛选     |
| W5 实体状态 | 已知对象是否进入目标状态，或满足可观察的条件？ | PR、CI、订单、成交记录、服务、资源可用性  | 对象身份、字段比较、状态转换和条件组合           |

分类由交给模型的事实决定。同一个数据源可以支持不同类别：训练日志可以提供 W1 的错误事件，也可以提供 W2 的 loss；股票 API 可以提供 W2 的价格，也可以提供 W5 的订单状态。

### W1 程序运行

关注一项有明确运行身份的工作。脚本报告运行状态和可观察的进展，不承担复杂的结果质量判断。

- 启动和结束：工作开始、正常退出、异常退出、被取消。
- 进展和阶段：处理计数增加、进入下一阶段、出现完成标记。
- 异常和疑似停滞：出现明确错误，或进度与日志超过约定时间没有更新。

需要保存运行身份、最近进度和已报告的转换。仅用 PID 时需要处理 PID 被复用的情况；重启或重新训练应视为新的运行。安静多久可以作为事件证据，是否卡死以及是否终止由模型结合任务判断。

### W2 数值指标

关注有名称、单位和采样时间的数值。脚本可以判断规则是否满足，模型负责解释原因和选择动作。

- 绝对阈值：显存超过上限、价格跨越指定值、指标出现 NaN。
- 相对变化：相对基线变化超过指定幅度。
- 持续条件：连续多次命中、持续超限、在时间窗口内没有改善。
- 趋势条件：斜率、波动、平台期等明确可计算的信号。

需要保存近期样本、基线和当前是否处于命中状态。缺失、过期和无效样本应单独处理；阈值附近反复波动可用连续命中或不同进入／退出阈值控制重复触发。指标变好不等于整个任务已经完成。

### W3 资源版本

关注有限、明确的资源集合，以及这些资源前后版本的差异。

- 产物生成：指定 checkpoint、评测报告或导出文件已经可读取。
- 内容更新：配置、文档、指定网页的选定字段或区域发生变化。
- 集合变化：目录中的文件新增、删除或替换。

需要保存资源身份、前一版本和已处理的差异。首次观察用于建立基线，是否报告初始内容应明确配置。生成中的文件需要检查写入完成条件；网页可先去掉时间戳、广告等无关区域，再比较指定内容。

### W4 新增信息

关注持续产生独立条目的信息流，以及条目与长期目标的关系。

- 新条目：新论文、新闻、公告、帖子或结构化披露记录。
- 规则相关：实体名、关键词、主题标签或字段规则命中。
- 语义相关：在确有需要时，用 embedding 等方法筛选候选。
- 后续跟踪：候选事件出现后，临时提高脚本检查频率，收集更新。

需要保存读取位置、已见条目身份、内容版本和候选事件。发布时间不能作为唯一去重依据；补发、乱序和同一条目的更新需要有处理规则。候选命中后只交接必要摘要、命中理由和原文引用，由模型按需读取更多内容。

### W5 实体状态

关注有稳定身份的实体和它的可观察状态。

- 状态转换：CI 从运行中变为失败，PR 出现新的审阅状态，订单变为已成交。
- 可用性变化：服务恢复、目标资源出现可用容量、指定内容变为可访问。
- 条件满足：某对象的几个字段同时满足要求。

需要保存实体身份、前一状态、版本或更新时间和已交接的转换。接口请求失败属于观测失败；不能据此断言对象进入了某个业务状态。来自网页或文本的推测应保留为候选证据，由模型核实。

## 时间触发与 Session 归属

时间是五类任务共享的触发能力。纯时间任务也可以单独存在，例如“今晚继续处理”或“每天生成一次摘要”，它不需要先观察数据源。

| 维度         | 可选方式                                       | 示例                                     |
| ------------ | ---------------------------------------------- | ---------------------------------------- |
| Session 归属 | 原 Session、独立后台 Session                   | 跟踪当前训练；后台持续关注新闻           |
| 检查时机     | 固定间隔、指定时间、周期日历、外部事件到达     | 每隔一段时间读取指标；收到更新后比较状态 |
| 交接条件     | 到点、变化、阈值、持续条件、相关性或它们的组合 | 到点生成日报；新增且命中关键词才交给模型 |
| 结束条件     | 一次触发、工作终态、截止时间、用户停止         | 提醒一次；训练结束；监控到指定日期       |

Session 归属表示处理结果的目标，不要求模型一直活跃。原 Session 的 Watcher 可以在后台运行；独立后台 Session 保存自己的目标、约束和历史判断。

检查时机和交接条件分别配置。例如“每分钟检查价格”属于 W2，但不意味着每分钟都调用模型；“每天总结新闻”属于 W4，并使用时间触发。

## 类别边界与组合任务

选择类别时先写出预期事件，再判断需要哪种检查逻辑：

| 预期交接的事实                   | 归类           |
| -------------------------------- | -------------- |
| 时间到了，需要执行下一轮         | 共用的时间触发 |
| 某次工作结束、异常或缺少进展     | W1             |
| 数值满足阈值、变化或趋势规则     | W2             |
| 已知资源与上一版本不同           | W3             |
| 信息流出现新的相关条目           | W4             |
| 已知实体进入某状态或满足字段条件 | W5             |

几个容易混淆的例子：

- 监控新闻首页指定区域是否改变是 W3；发现新闻源里的新文章是 W4。
- 发现目录里的新 checkpoint 是 W3；判断训练是否停止是 W1；跟踪验证分数是 W2。
- 发现新的监管披露记录是 W4；跟踪已知申报的审核状态是 W5。
- 日志、RSS、HTTP、文件系统和浏览器是数据来源或采集方式，按预期事件选择类别。

复杂任务可以组合多个类别，共享一个长期目标，无需为每个业务领域再建立新类别。

| 长期目标                   | Watcher 组合                      | 交给模型处理的工作                 |
| -------------------------- | --------------------------------- | ---------------------------------- |
| 关注一轮训练直到结束       | W1 运行状态 + W2 指标 + W3 产物   | 判断训练健康度、解释异常、验收结果 |
| 持续关注某主题新闻         | W4 新条目 + 关键词筛选 + 定期复盘 | 核实事件、分析意义、决定是否通知   |
| 关注价格和相关消息         | W2 价格 + W4 新闻                 | 综合证据、解释变化、形成结论       |
| 成交后在期限内完成后续操作 | W5 成交状态 + 时间触发            | 检查下一步义务并执行约定操作       |
| 每天生成信息摘要           | W4 增量采集 + 时间触发            | 整理、筛选和生成摘要               |

“事件发生后在期限内完成下一步”属于有时限的组合任务，需要保存尚未完成的义务。单次模型运行结束后，这个义务仍然存在。

## 检查频率与模型处理

各类别共用三个阶段；具体间隔和阈值由任务的变化速度、响应要求与预算决定。

| 阶段     | 代码做什么                             | 模型何时运行                             |
| -------- | -------------------------------------- | ---------------------------------------- |
| 常态观察 | 增量采集、比较状态、执行简单规则       | 周期处理到点，或出现需要交接的事件       |
| 候选跟踪 | 在限定时间内提高检查频率，累计证据     | 候选达到交接条件，或需要模型判断如何继续 |
| 模型处理 | 提供触发原因、时间、必要证据和读取引用 | 分析、行动、更新记忆与监控策略           |

候选跟踪需要明确进入、退出和最长持续时间。Watcher 根据已配置的规则调整检查节奏；Harness 执行调度并限制总开销。模型处理完成后，可以更新规则或恢复常态观察。

状态至少需要区分“成功观察但没有候选变化”“出现候选变化”“无法完成观察”。连续无法观察可以触发单独的故障处理，避免把失效的监控器显示成正常安静。

## 后续模板验证范围

首批范围为五类基础探针加一个共用定时器。下表描述分类阶段的目标范围；已实现参考包的名称、输入格式和配置方式见 [参考模板](../.pi/skills/virtual-agent-authoring/templates/README.md)。通过可控输入测试的规则仍需按真实来源验证采集适配。

| 候选模板     | 覆盖类别 | 首批范围                           | 该模板必须验证的边界                           |
| ------------ | -------- | ---------------------------------- | ---------------------------------------------- |
| 程序运行探针 | W1       | 明确身份的本地程序，结束和进度信号 | 正常结束、异常结束、运行替换、安静但正常工作   |
| 数值规则探针 | W2       | 结构化指标，阈值和连续命中         | 单位、无效与过期样本、抖动、进入与退出命中状态 |
| 资源版本探针 | W3       | 本地文件或选定内容的版本比较       | 初始基线、重复版本、删除重建、写入未完成       |
| 增量信息探针 | W4       | RSS 或结构化列表，条目去重和关键词 | 初次积压、乱序、补发、内容更新、不相关条目     |
| 实体状态探针 | W5       | 结构化 API 中的稳定实体和字段      | 对象消失、状态回退、重复状态、请求失败         |
| 定时触发器   | 共用能力 | 一次性时间和固定间隔               | 同一时点重复执行、重启、到期、暂停与取消       |

所有模板都应覆盖首次运行、无变化、命中、重复输入、观测失败和重启后的状态恢复；同时明确“只记录”“提高检查频率”“交给模型”各自的条件。候选命中不直接等同于通知用户，通知由目标对应的处理逻辑决定。

模板成为“已验证”需要留下版本、可重复的样例或用例、实际验证结果和适用边界。可复用的是采集、比较、状态保存和事件输出；具体目标、阈值、关联 Session 和模型处理说明属于任务实例。

首批端到端验证任务选择“当前训练的持续监控”和“后台新闻源的持续关注”，分别覆盖原 Session 与独立后台 Session。先用可控输入验证基础模板，再验证目标来源的实际行为；embedding、多源关联、浏览器采集和复杂趋势可以在基础模板稳定后扩展。

## 与既有设计的关系

本分类用于选择和验证监控逻辑。它不把类别直接规定为 Runtime 的类名、工具参数或业务路由，也不替代现有 Watch Program、Watcher 和事件处理 Agent 的职责划分。

- 长期目标与监控器集合沿用 [Watch Program 设计](watch-program-design.md) 的概念。
- 作者编写、校验和显式登记的流程见 [Virtual Agent 作者技能](../.pi/skills/virtual-agent-authoring/SKILL.md)。
- 跨运行保存、休眠和恢复的背景见 [长程任务设计](long-running-agent-design.md)。

执行合约、会话/后台归属和管理页面见 [目标架构](long-term-goals-architecture.md)。动态冷热频率、Embedding 筛选与更广的真实来源适配仍为扩展方向，不因本页列出就视为已支持。
