# M1 个人情境与已有安排：实现设计

更新日期：2026-11-05。对应 [M1-01 至 M1-05、R1/R2/R6、S1/S2/S9](personal-assistant-roadmap.md)。状态：领域、存储、两条 Pi 聊天路径、当前请求投影及设置管理已接入；事项引用、Inbox 投递和完整 M1 验收仍待完成。当前入口和内部合同分别说明已实现行为，其后章节保留完整集成设计，不能视为全部交付。专项正文暂为中文。

## 用户效果与交付范围

首个闭环是：用户在对话 A 授权保存临时状态或已有安排，在相关对话 B 中获得基于当前事实的帮助；纠正、取消、结束、过期或删除后，新请求和旧执行的提交检查都使用最新状态。记录一次安排不会自行开启监控或创建目标。

采用统一的情境记录与变更规则。会议、旅行、预订作为合成验收资料，不各自建设工作流。跨事项自动重评估、冲突分析、外部采集和净收益提醒分别留在 M2/M3；此设计只提供它们所需的事实引用、版本和变化投递边界。

| 用户表达（合成）                               | M1 应有行为                                                            | 不可推断的内容                                   |
| ---------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------ |
| “记住我这两天身体不舒服，相关安排要考虑这一点” | 明确处理范围和可解析的有效期后保存临时状态；只向相关请求提供必要约束   | 不判断疾病，不自动取消会议；时效不明先澄清       |
| “周五 10 点有会，按上海时间保存”               | 依据宿主提供的日期解析，存来源、时区和已知时间；结束时间未知则保留未知 | 不补造结束时间，不把登记变成持续目标             |
| “酒店准备订，先别当成已经订好”                 | 保存为意向或待核实安排                                                 | 不标记已确认，不推断价格和退改规则               |
| “改到下周”“已取消”“不要再记这件事”             | 对明确指向的记录进行版本更新、取消或删除；指向不明时询问               | 不修改近似名称的其他安排，不让旧结果重新创建记录 |

## 聊天与设置的当前入口（M1-05）

启动开发项目后，在“设置 → 情境与安排 → 使用情境与安排”开启使用。在对话 A 明确说“请把我的上海出差保存为跨对话个人情境：2027 年 6 月 10 日 9 点至 12 日 18 点，上海时间，行程已确认”，再在新对话 B 说“帮我安排上海出差期间的会议”；相关模型请求会获得当前版本。示例是合成资料，不代表用户的真实行程。改期、取消或遗忘可在聊天明确提出；设置页可查看全部记录、标记取消/结束、删除，也可在使用关闭时管理。

工具 `manage_personal_context` 支持 `query/save/update/forget`，模型不能传入数据根、消息身份、权限或敏感许可。保存/更新需要完整 `context`，纠正与删除需要当前 `id/revision`；`query` 可按已知 `id` 读取。宿主从当前原始用户消息取得 quote、消息 ID 和接收时间，替换模型的 observedAt；Dashboard 附件正文、普通工具结果、human/inbox 内部请求不作为新登记授权。Dashboard 使用持久 composer 身份；CLI 使用原会话分支中的用户消息条目 ID 与接收时间，不从压缩后的合成 user 摘要签发授权；内部 Run 使用原 Run 身份，恢复时取原 checkpoint prompt。人类问答及排队消息的持续授权接入仍待验收，不从拼接文本推断。

`temporary_state` 只表示本人的临时状态，状态值为 `active/ended`，必须有 `validUntil` 或 `reviewAt`，禁止 `startsAt/endsAt/timeZone`；计划、待办意向或“晚上询问是否参加”用 `arrangement`，不确定事项用 `tentative`。安排日期、时刻未知时可留在正文，不为通过校验补造时间戳。工具参数说明与校验错误同时给出这些条件。

引用优先精确匹配；只允许空白展示差异（如不换行空格变普通空格），匹配后换回可信原消息的实际片段再做独立语义检查和落盘。文字、日期或其他内容改动仍拒绝，不将空白匹配当授权。工具包装格式兼容与此来源匹配分开处理。

同一消息内参数校验失败最多允许一次纠正；第二次失败后阻止进一步写入。语义拒绝、来源拒绝、版本冲突或提交错误后直接阻止同消息的后续写入，换类型、标题或可见范围不能绕过。错误码为 `invalid_request` 或 `write_attempts_exhausted`，错误不回显原始参数。此纠错预算属于当前聊天适配实例，不是跨进程持久重试许可；既有持久代次和提交屏障继续约束恢复。读取仍可用。

保存/更新返回 `reminderScheduled=false`：只登记情境，不创建定时通知或后台目标。提醒请求需要独立调度能力和明确的时间等条件；未调用并核实调度结果前不能承诺“到时提醒”。`reviewAt` 仅用于情境待复核判断，也不是提醒触发器。

对 `arrangement`，若原始消息没有可识别的钟点依据（数字/中文钟点、ISO 时刻、noon/midnight 等），宿主省略模型新增的 `startsAt/endsAt/reviewAt/validFrom/validUntil`，在结果的 `timeFieldsOmitted` 和提示中说明未保存；日期、季节、模糊晚上保留在正文。状态更新保留与已有记录相同的已知时间。该门槛只限制无钟点时的新增时间，不证明含钟点的整段表达、相对日期或多个事件时间都已正确理解，仍需独立语义校验。临时状态的有效期合同不变，旧记录不会自动迁移。

每次变更有独立、无工具、20 秒超时、最多 768 输出 tokens 的模型语义检查，复用当前连接，不自动重试；校验整条用户表达与候选的归属、内容、状态、时间、范围和处理意图。假设等明显反例还先由宿主拦截。检查失败、来源不清或时间含糊时不落盘；真实模型对自然语言的识别质量仍需单独验收。开启“从对话登记”后允许模型对明确本人陈述提出登记，不扫描历史，不启动空闲采集；关闭时仍允许明确的一次保存。敏感处理独立默认关闭，目前一次敏感保存也需在设置开启该项。

语义检查响应只接受纯 JSON 或单个完整的 JSON 代码块（`json` 标签或无标签）；归一化展示格式后仍按严格 schema 校验。不从说明文字或多段代码块中猜取对象，不修补残缺 JSON，不把拒绝改为许可。检查响应限 16384 字符，截断、语法或 schema 失败统一返回 `assessment_invalid`，不泄露原始响应片段，也不自动重复写入。原始用户消息及工具参数不走该格式归一化。

使用、对话登记、敏感处理均默认关闭，设置页显示记录不等于向模型提供记录。使用关闭时仍显示无正文的功能开关；每条可信用户消息均提供接收时间与宿主时区，相关性或开关关闭不能使模型失去相对日期依据。相关性同时接受个人安排/健康话题、第一人称日期行动意图，以及个人事项概览：“最近我有什么事”“我接下来要做什么”、带时间的省略主语问句“最近有什么事”和相应英文问法。查询、投影与旧快照刷新共用此规则；代码及假设/第三方请求不投影正文。未识别的查询返回 `request_not_relevant`，不再混同权限拒绝，也不表示开关关闭或记录缺失。此版本仍为有限规则，不是通用语义检索：“继续”“改到周五”等省略指代可能需要补充事项；概览只包含当前获准范围内的已登记情境，不代表已查阅外部日历/待办。用户级安排在相关请求中会一起提供，尚未按具体事项建立精确影响集合。

每次请求及压缩后的请求都刷新宿主投影；查询结果与投影最多 20 条、9000 字符，`truncated` 标记省略，支持按已知 ID 补查。预算不够时省略正文，尽可能插入“未完成情境检查”状态，不截断用户消息。历史工具查询带 epoch/generation、快照版本、消息身份与当前有效性；删除、关闭、敏感许可或时效变化后，下一次请求剥离旧工具快照。原聊天、模型已读内容与既有请求档案不在删除范围。

运行中改变开关会使当前消息的授权代次过期，旧请求返回 `conflict` 且不自动重试写入；应在设置稳定后重新发送请求。冲突不证明记录已取消或删除。刷新只撤销旧查询快照，保留失败工具调用的真实错误，不能把保存失败、参数或权限错误改写为“记录已撤销”。敏感事项仍需独立开启敏感处理，不通过重新发送绕过该开关。

同一用户消息每种类型/可见范围至多保存一条，模型换 tool-call ID 或标题不能绕过去重；多条同类安排需另发消息。容量仍按既有 schema 有界失败，不清空消息屏障或静默丢弃事件；长期容量维护、事项引用、Inbox 消费、受控外部动作前/提交检查和完整恢复授权仍待后续接入。本批提供可在聊天中体验的登记/读取/纠正闭环，不代表 M1 全部验收或主动照看已交付。HTTP 字段见 [Product API](product-api.md#personal-context)。

## 已实现合同（M1-03/04）

[领域](../src/domain/personal-context.ts)、[存储](../src/runtime/personal-context-store.ts)、[内部服务](../src/runtime/personal-context-service.ts)已实现，回归入口为 [personal-context tests](../test/personal-context.test.js)。本机用户情境库与既有稳定记忆共存，不替换现有跨对话记忆或目标交接。

| 内部操作                                   | 当前行为                                                                                                                                                                                    |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PersonalContextService.openRequest(host)` | 宿主提供真实消息身份、原文、接收时间、用途、操作身份和权限。按工作区根、Task、原消息 ID 持久记录 generation；更换 Run 或重启不把旧消息当新授权。所有这些参数都不能直接绑定模型输入          |
| `save/update`                              | 严格参数校验；调用必须显式提供的宿主 `assess` 判定自述/不确定/假设/第三方、敏感性与保存授权。引用匹配只是附加校验，不是语义授权证明。记录当前版本和无正文事件一起提交；不调用模型或创建目标 |
| `query(ids)`                               | 最多 20 个明确 ID，按当前启用状态、请求代次、用途、敏感许可和 task/project/user 范围过滤；返回记录及 validity。尚无自然语言搜索或自动请求注入                                               |
| `configure/forget`                         | 设置变更或删除抬升 generation；阻断旧请求写入及旧许可。删除移除正文与相关旧事件，清空正文参数摘要收据，保留不含正文的请求身份屏障；已知 ID/版本可在使用关闭或记录许可到期后明确删除         |
| `prepareExecution/validateExecution`       | 只有宿主提供实时 `canExecute` 检查时才签发进程内不透明许可；复核 epoch/generation、整个快照版本、记录 revision 及当前有效性。复制、伪造或跨请求/重启复用许可均拒绝；恢复后必须重新申请      |
| `pendingChanges/acknowledgeChange`         | 只保存和确认无正文事件；关闭使用时不提供待投递列表，确认需匹配当前 epoch/generation，重复确认不改变事实。尚无消费者写 Inbox，也无自动唤醒                                                   |

当前 schema 限定 200 条记录、256 个待确认事件、512 个操作收据、1024 条消息身份屏障，快照最多 2 MiB；正文每条 2000 字符、来源引用 1000 字符、标题 200 字符。达到上限报 `capacity`，不静默清理事件或重放屏障，也没有自动整理/清理入口。接入长期运行前需提供可恢复的容量维护方案，不能靠清空屏障绕过上限。错误码包括 `conflict`、`permission_denied`、`source_rejected`、`assessment_invalid`（聊天语义检查失败）、`request_not_relevant`（未识别为个人规划或概览查询）、`invalid_request`、`write_attempts_exhausted`、`not_found`、`inactive`、`capacity`、`storage_invalid`；结构错误由 schema 拒绝，聊天入口映射为不携带来源全文的诊断。

已实现状态区分 `reported/uncertain`，不接受模型自报 verified。临时状态必须有到期或复核时间；意向、不确定、已过安排时间及待复核记录不能取得执行许可。更新必须同 ID/当前 revision，类型与范围不可就地变更；更换范围需新的明确操作设计，不通过自动合并扩大范围。当前不接收模型任意关系引用，已有目标/资源的引用校验留在集成阶段。

`enabled/registrationEnabled/sensitiveEnabled` 的持久设置默认关闭，内部写入必须由宿主提供授权判断。聊天路径已接原始用户消息与独立模型检查，允许明确的一次保存或已授权的本人陈述登记；不运行后台采集。内部服务支持单次敏感许可，当前聊天入口只使用独立敏感设置。读取另检查用途与许可期限；测试中的确定性 `assess` 回调不证明真实模型识别质量。

快照损坏、未知版本、超限和并发冲突均保留已提交文件；同目录私有临时文件经 sync 后复用 Windows 有限重试的原子替换。在锁内、确认当前文件可读及候选写入合法后，清理本模块精确命名为 `context.json.tmp-<UUIDv4>` 的遗留普通文件；不删除相邻文件、目录或符号链接，避免删除后仍有崩溃临时快照留下正文。请求与操作身份由宿主稳定派生，尤其不能把每次模型重试的新 tool-call ID 直接当作新操作。没有自动迁移旧记忆、回滚用户数据或从备份恢复的入口；恢复备份需停止宿主并更换存储 epoch 后独立验收。内部存储的 transaction 是可信运行时接口，禁止开放给 HTTP、模型或外部工具。

## 领域合同

先限定单本机用户数据根，不宣称多用户隔离。`ownerKey` 由宿主的数据根身份确定，不接受模型自报用户。项目使用既有宿主归属；Task/Run 引用同时保留真实 task-storage-root 的宿主引用，不能只凭 Task ID 在不同工作区间关联。

| 字段组   | 必需信息与规则                                                                                                                                   |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 身份     | 宿主生成 UUID `id`，正整数 `revision`，`createdAt/updatedAt`；名称和语义相近不代表同一记录                                                       |
| 类型     | `kind=temporary_state/arrangement`；稳定偏好仍交给既有记忆；事项目标只保存引用，不复制 Goal 状态                                                 |
| 事实状态 | `evidenceStatus=reported/verified/uncertain`；模型提取先是候选。明确用户自述可为 reported，外部证据验真才为 verified；反复推断不升级             |
| 业务状态 | 按 kind 判别：安排使用 `tentative/confirmed/cancelled/ended`，临时状态使用 `active/ended`；active 仅表示当前报告，仍需标明来源，不能表示专业认证 |
| 内容     | 最小必要标题、事实和行动约束；未知金额、条件、缓冲等字段缺省，不能填 0 或空值冒充已知                                                            |
| 时间     | `observedAt`、可选 `validFrom/validUntil/reviewAt`；安排单独保存 `startsAt/endsAt` 与 IANA `timeZone`，原表达只保留必要片段                      |
| 范围     | `visibility=task/project/user` 与对应宿主身份；跨任务记录需明确范围，user 不代表可向所有 Task 无差别注入                                         |
| 关联     | 可选现有 `taskRef/goalRef/resourceRef` 与 `relatedContextIds`；校验存在、归属及读取权限，不能自动创建目标                                        |
| 来源     | 宿主确认的用户消息或已回答问题身份、Task/Run、接收时间及最小原文片段；M3 才扩展真实外部来源                                                      |
| 处理许可 | 宿主签发的 `consentRef`、用途、保存范围和设置版本；事实内容不能充当工具权限或对外行动许可                                                        |

`uncertain` 与已取消记录可通过管理查询查看，不作为已确认的安排或现行行动约束。登记需通过 schema、来源和处理许可检查，不能只检查引用是否为用户消息的子串；来源真实性由程序核验，是否确为自述/保存意图还需语义判断，无法确定时询问。

安排缺少结束时间可保存，但不能据此声称没有时间冲突。相对日期按用户消息接收时间和宿主时区解析，保留解析依据；“周五”等存在实质歧义时澄清，不按开发机器时区补猜。时间区间用 `[start,end)`，`end <= start` 拒绝；未知/仅日期精度单独标记，不能伪造午夜瞬时点。DST 重复或不存在的本地时间需明确偏移或澄清。

## 状态、纠正与时效

事实生命周期和有效性分开：`expired/not_yet_valid/needs_review/current` 是根据时间、处理许可与业务状态计算的查询结果，不覆盖用户事实。不持久保存依赖“现在”的 current 布尔值。

| 操作          | 条件                                         | 持久结果和后续读取                                                            |
| ------------- | -------------------------------------------- | ----------------------------------------------------------------------------- |
| 登记          | 新请求、可信来源、有效处理许可；有宿主幂等键 | 新 ID、revision=1、最小事实与投递意图；不创建 Task/Goal                       |
| 纠正/改期     | 当前 ID、expectedRevision 和许可版本匹配     | 同 ID、revision+1，替换当前事实；旧快照不能覆盖                               |
| 确认安排      | 有明确依据且原记录未取消/删除                | 标为 confirmed，保留新的来源；不推断付款或履约                                |
| 取消/结束     | 明确指向及当前版本                           | cancelled/ended，revision+1，不再作为未来安排约束；不执行外部取消             |
| 到期          | 查询时检查 `validUntil/reviewAt`             | 停止作为现行约束或返回待复核；不宣称康复、会议已开或订单已履约                |
| 删除          | 用户管理操作，即使使用已关闭也允许           | 清除正文、来源片段及待投递正文；抬升存储 generation，阻断所有旧候选及执行许可 |
| 关闭使用/撤权 | 宿主可信设置或明确管理请求                   | 抬升 generation，后续投影为空/受限，旧提交失败；不自动重开                    |

不采用“找不到就创建”的更新回退。已取消后重新启用也需新的明确用户请求和当前版本，不由过期事件恢复。同一表达与既有记录的关联由模型提出，宿主验证 ID 和版本；没有足够依据时保留候选或询问，不靠标题相似度静默合并。

## 处理开关、范围与最小保存（M1-02）

新增情境设置与稳定记忆设置分开，首次默认关闭。方向确定如下，具体 UI 文案随 M1-05 验证：

- 情境使用：控制向请求提供已有情境，关闭后保留记录供用户管理；不改变现有记忆开关。
- 对话登记：允许在已说明的范围内从明确用户表达提出并保存情境；默认关闭，不收集全部历史对话，不增加空闲自动学习请求。
- 敏感情境处理：默认关闭；健康等敏感信息另需用途和有效范围，不能因开启一般情境功能顺带开启。无法可靠区分是否敏感的候选按需澄清或拒绝保存。

明确的一次保存请求可以授予仅该记录的处理许可，不自动开启全局登记。若使用仍关闭，告知已保存但不会跨任务使用，并允许用户明确开启使用；不暗中改变开关，也不每轮重复确认已明确授予的范围。敏感类别的持续处理需要独立授权，不以模型判断用户“可能需要”替代。

读取遵循范围和用途的交集：用户级记录先经宿主范围过滤，再按当前请求目的获取最小事实；项目记录仅当前项目可见；任务记录不跨 Task。模型可在获准范围提出相关查询，但“返回全部个人状态”不能作为默认请求准备。未知用途不注入敏感正文，管理查看走独立用户操作。Subagent 默认只获得父任务当前工作必需的约束摘要，不能继承整个用户情境库。

对外工具只获得本次动作必要字段，不能把个人情境全文放入搜索、邮件或网页。保存/跨任务使用许可不等于监控、发送、改约、退款、购买或删除外部数据的许可。权限记录只接受宿主可信用户输入；附件、网页、Inbox 来源事件和模型输出不具有授予或扩大许可的能力。

删除承诺限定于新增情境库、投影和未发送事件；不声称能擦除原会话、已有请求快照、备份或已发送至外部的内容。实现时须在用户删除入口说明实际范围。投递只带 ID/版本/变更原因，不复制敏感正文到新日志；旧模型响应、错误和 tracing 同样不回显已删除内容。

## 存储、一致性与恢复

规划路径为 `<ATRIA_HOME>/personal-context/context.json`，由宿主 [数据路径](task-workspace-layout.md) 解析。它与稳定记忆及 Task 分开，所有入口对同一数据根复用存储；测试使用自己的 mkdtemp。版本 1 快照包含：存储 `epoch`、撤权/删除屏障 `generation`、每次情境变更递增的 `snapshotRevision`、处理设置及版本、当前记录、非正文幂等收据、待投递事件和投递状态。数据目录不纳入 Git 或发行包。

每次写操作：入口验证 → 在锁外完成候选提取 → 取短文件锁 → 重新读取并严格验证快照 → 校验 generation/授权/记录版本 → 同快照写当前状态和投递意图 → 同目录临时文件 flush/sync → 用 [replaceFile](../src/storage/replace-file.ts) 原子替换。锁内不运行模型、外部网络或 Inbox 写入。遵循已有有限 Windows 占用重试，不先删除旧文件；原子替换不等于断电后的完整事务保证。

幂等键来自宿主持久用户消息身份与工具操作身份，不能由模型任意换 key 绕过去重。相同 key 与相同规范化参数重放返回收据；相同 key 参数变化返回冲突。删除/撤权提升 generation 使所有旧请求失效，重新保存必须来自新用户请求；因删除而失效的旧请求不能以创建新 ID 逃逸。收据不保存正文，清理时抬升 generation，不允许旧 key 在清理后重新执行。

到期在每次查询和提交时计算，不靠后台计时器才能失效。事件过期和容量上限必须由 schema/设置有界约束；达到上限返回可见错误，不静默删除事实或待投递事件。实现前在失败测试中固定上限与边界值，不能在压力下自动扩大范围。

首次没有文件时视为关闭且空白，不导入历史记忆或扫描任务。格式损坏时保留原文件并报告可定位错误；写入与依赖情境的提交失败关闭，不把损坏读成“没有约束”。不依赖情境的普通聊天可继续，但不能声称已检查个人安排。未知新版本拒绝覆盖。

回退不迁移旧用户记忆或目标文件。新模块关闭后旧功能继续运行；只产生新增目录，新格式文件保留供再次升级。恢复备份是显式维护操作，须停止相关宿主并更换 generation 所属的存储 epoch，不能恢复出与旧执行许可相同的身份。用户删除内容不能通过自动修复或备份回放重新进入现行库。

## 变化事件与既有事项

事件最小内容为宿主生成的事件 ID、存储 epoch/generation、记录 ID/revision、原因、创建时间和已登记的接收引用；没有正文。事实与事件同快照提交。M1 只向已明确关联的事项投递；没有接收事项时保留事实，不凭登记新建后台任务。推断新的影响关系属于 M2。

`personal-context-delivery` 由既有服务周期和启动恢复入口调用：读取待投递记录 → 在锁外用稳定 messageId 写既有 Inbox → 成功后在快照短锁内标记接收方收据。崩溃在 enqueue 后、收据前会重放同一个 messageId；Inbox 接受不等于事项已完成。投递不跨文件声称原子，接收方必须再读取当前版本。

删除取消该记录的旧待投递事件，并留下无正文删除事件。当前关闭使用时保留引用事件但不提供待投递列表；设置变更后引用事件使用新 generation，后续消费者仍须读取当前事实和授权，不能凭旧事件执行。已发送消息到达时发现版本/许可失效即丢弃。暂停目标可保留待办，但不得启动 Main 或新建替代目标；显式恢复后再读取当前状态。来源失效、无法定位原 Task 存储或目标结束分别保留可见状态，不把失败解释为成功或没有影响；实际消费者尚待接入。

## 请求投影与提交检查

每次新用户请求、内部续执行、回答恢复以及压缩后，宿主从当前存储准备投影。投影带 `contextRefs={id,revision}`、store epoch/generation 和许可版本，持久执行记录只保存必要引用，不把整个情境库写进 Task memory。历史摘要内的旧事实不是权威来源。

宿主先用范围和用途约束检索，再让模型做复杂相关性判断。投影有独立预算；预算不足时省略并返回“情境未加载完整”的宿主状态，涉及安排的行动应按 ID 查询，不能将省略当作没有安排。不得为了塞进情境而截断用户消息或悄悄扩大模型输入预算。

版本检查由 `personal-context-service` 提供短期、宿主持有的执行许可：

1. 执行前核验请求身份、store epoch/generation、所依赖记录版本、有效时间、用途与目标暂停意图，返回可核对的依赖快照。
2. 调用受控领域动作前及结果提交前再次核验；许可到期、事实/授权变化、暂停或删除返回具体冲突，废弃旧方案并读取当前状态。只比较 generation 不足以覆盖记录改期，必须同时核对每条 revision。
3. 新的相关记录在模型生成期间加入也可能改变方案。M1 先使用每次情境变更都会递增的快照版本作为保守检查，允许无关更新导致一次重新评估；M2 有证据后再收窄影响集合，不能只检查已读记录而漏掉新增约束。
4. 对本库的最终写入，校验与落盘在同一短锁中；跨领域动作不能在校验后承诺消除竞态。有原生 CAS 的驱动将资源版本一起提交，无条件写接口只能明确保证最后一次检查的时点和结果不确定边界。

Pi 的 `tool_call` hook 可作为受控工具的前置检查入口；PiSession 的工具包装调用同一服务。两条路径都要通过真实生命周期测试确认顺序和失败传播，不能只加提示词。提交检查放在实际领域服务的写入边界，不能只依赖模型携带 refs。

现有通用 bash、任意文件工具和外部软件没有覆盖所有业务副作用的事务边界。M1 不宣称提供全工具的撤权后阻断；依赖个人情境的对外改约、退改和购买在完成对应受控 Adapter 前不提供自动执行能力。已开始且无法撤回的外部动作先查询实际结果，不自动重试。恢复会重新核验，精确请求重放也不能绕过当前授权和版本检查。

## S1/S2/S9 与对抗性验收合同

确定性领域和存储规则已由本批内部服务测试覆盖；以下完整跨对话场景仍待 M1-05/06，不能因内部测试通过而记为 S1/S2/S9 已验收。时间由可注入时钟控制，数据与服务隔离；本地假模型要驱动真实 Pi 工具、跨 Task 请求和进程重启，最终独立读回状态。

| 场景           | 输入与动作                                                             | 可观察的验收结果及反例                                                                                        |
| -------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| S1 跨任务情境  | A 明确授权保存有效期两天的临时不适；B 请求安排工作，C 请求处理无关文件 | B 获得必要限制及来源；C 无私密正文；关闭使用后 B 不再得到状态。假设、引用、为他人写作、无保存许可均无正式记录 |
| S2 纠正与失效  | 在旧模型生成时纠正状态、推进时钟到期、关闭或删除；重启后重放旧结果     | 纠正仍是同 ID 新版本；到期不继续约束且不宣称康复；旧提交得到冲突；删除后正文不存在，重复重放不能重建          |
| S9 已有安排    | A 登记会议、意向预订和明确已订预订；B 查询后，A 改期或取消，重启 B     | B 只使用最新版本；意向不晋升已订；时区与未知条件保留；不新建 Goal；取消记录不作为有效行程；时间经过不证明履约 |
| 消息与授权     | 同一消息重复投递、模型更换操作 key、外部文档伪装许可、超时推荐项       | 无重复记录或授权升级；同 key 不同参数冲突；未回答的问题不视为同意；旧 Run 不能借旧用户原文扩权                |
| 并发与恢复     | 两个宿主改同版本；事实写完/投递前、enqueue 后/收据前中断               | 只有一个旧版本写入成功；事实与意图一起存在；重启补投稳定身份消息，接收者读当前事实；不重复用户动作            |
| 范围与最小披露 | 同名 Task 位于不同根、切换项目、委派、模型投影预算不足                 | 不串归属；无关项目/子任务拿不到全文；预算不足可见且行动需查询补全                                             |
| 文件与控制     | 损坏/未知版本文件、Windows 占用、暂停后迟到事件、备份恢复              | 保留可恢复文件，有限重试；失败不当作空状态；暂停不唤醒；旧 epoch/generation 不获重新授权                      |

完成 M1 还需一次单独的实际模型验收，评估真实语言对自述、假设、纠正和指向不明的判断。模型判断无法由 schema 完整证明；不得以引用匹配或假模型结果代替该证据。
