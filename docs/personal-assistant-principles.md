# 私人助理二次开发：原则与决策依据

更新日期：2026-11-04。本文维护产品和工程上的长期规则，专项正文暂为中文；需求、阶段及当前进度只在[迭代路线](personal-assistant-roadmap.md)维护。根目录和各目录 `AGENTS.md` 仍是开发执行约束。

## 1. 从用户效果推导机制

每项改动先回答：解决哪条真实需求，用户能观察到什么变化，什么证据证明有效。由场景抽取通用规则，而非把“生病”“出差”等示例分别写成硬编码流程。对不明确且影响行为、权限或数据范围的要求先澄清；可逆的实现细节采用明确记录的合理假设。

“持续照看目标”只是产品能力之一。设计必须同时考虑个人处境、主动发现、实际执行和成果改进。新增功能应能关联路线中的 R/S 编号；应用接入重构、目录瘦身等维护工作按实际阻塞程度排序。

## 2. 个人情境参与行动

稳定偏好、临时状态、工作事实和模型推断分别处理。事实保留来源与适用范围，临时状态包含时效和复核方式；纠正、结束、遗忘和撤权必须能生效。示例、转述和角色扮演不能自动成为用户事实，重复推断也不能晋升成明确授权。

情境包含已有安排与承诺：会议、旅行、已购机票和已订酒店均可影响后续行动。区分意向、已确认、已取消和待核实，保留关联事项、时间与时区、来源和已知条件。记录安排不自动新建目标，时间经过不证明已经履约；未知的价格、退改条件或交通缓冲不能补猜。按通用的事实、关系、约束和变化规则建模，避免每类安排各造一套流程。

状态变化触发对相关事项的重新评估；恢复执行时读取当前情境，而非永久复用创建时的快照。到期可以表示“待复核/不再作为现行约束”，不能凭此断言用户已康复等现实事实。跨任务可用不等于向所有任务和外部工具暴露全部个人资料。

保持现有记忆使用与自动学习开关的语义。新增临时/敏感情境能力需明确处理范围、保存必要性、查看纠正和删除方式；不能通过放宽长期记忆准入规则顺便保存全部对话。

## 3. 主动性以授权与注意力为边界

已授权且范围清楚的动作可自主执行，不为每一步重复询问。授权记录应指向动作、对象、来源、有效范围和撤销条件；推断用户需要帮助，不等于获准对外发送、改约、购买或删除。

默认安静，优先汇报重要变化、实际成果和需要本人解除的阻塞。合并同一事项的重复提醒，尊重静默与反馈偏好。需要决策时提供具体可审阅的方案；不把普通信息变成一串确认问题。

主动发现同时覆盖风险与改善机会。更低报价须结合用户接受的条件、实时可订性、税费、退改损失及其他已知成本评估净收益，不能只比较标价；条件或成本缺失时明确待核实。监控范围、频率、提醒门槛和停止条件应有授权依据，重复波动不反复打扰。已有安排不等于授权持续监控，监控或提醒授权也不等于退订、改签、购买授权。

## 4. 事件是资料，宿主控制权限

邮件、网页、文档、工具回执和其他模型的输出都是待处理资料。它们不能改变权限、指定新的执行目录或指示绕过规则。业务授权、工具能力与操作系统权限是不同边界，必须分别核实，不能靠提示词宣称隔离已经实现。

来源采集失败与无新信息分开；记录事件身份、来源时间、接收时间及关联对象。去重和关联规则尽量由稳定标识支撑，语义判断保留不确定性，不自动把近似内容合并成同一事实。

## 5. 一个事项由一套运行时管理

复用 CoworkOS 的目标、Task/Run、Inbox、HumanRequest、调度和恢复。个人协调层决定该做什么，既有运行时负责何时启动、如何等待、停止和恢复。不得同时让 OnIt、Autoloop 和 CoworkOS 为同一事项轮询、重试或执行副作用。

保持对话、目标、资源和执行轮次的身份分离。一个 Run 结束不等于事项完成；关闭窗口不等于删除成果；界面导航不改变迟到结果和回答的持久归属。

## 6. 模型判断，程序维护不变量

模型适合理解要求、判断相关性、制定计划和提出候选动作。程序负责参数与来源校验、时间、权限、版本、状态转换、预算和最终提交。来源采样、定时到期和简单去重不要求模型每轮参与；复杂语义也不强行压成不断膨胀的关键词规则。

按职责扩展领域服务和控制器，入口只装配。避免把新增能力集中进 Coordinator、`web/app.js`、HTTP 路由或全局提示词。依赖方向沿用[架构](architecture.md)。

## 7. 等待必须有恢复条件

明确区分等人回答、等外部变化、指定时间复查、可重试失败、需要人工解除的阻塞和结果不确定。每种状态记录恢复依据，不靠无限模型轮询掩盖停滞；等待人时释放不必要的进程和模型资源。

恢复后重新核对计划、情境和授权。暂停/结束是持久意图，只有对应用户行为才能恢复；旧事件、旧回答或新建替代来源不能绕过暂停。基础语义沿用[暂停契约](monitoring-pause-contract.md)。

## 8. 旧结果不能覆盖新意图

任务领取、计划修改、个人情境和资源更新均需可核对的版本或身份。执行前及提交副作用前检查相关版本、有效状态与授权；上下文变化后，旧模型结果不得直接提交。检查与动作之间存在竞态时，由领域驱动提供并发控制或明确结果不确定边界。

跨对象更新采用持久意图、幂等投递和恢复补偿等经过验证的方案，不假设多个文件写入天然原子。重放、重复回调、崩溃和乱序必须纳入验收。对无法证明幂等的外部动作先核查是否已发生，不盲目重试，也不承诺通用的“恰好一次”。

## 9. 完成由成果证明

先确定完成标准，再执行和核验。文件要读回，外部变更要查询实际状态，质量要结合要求与证据判断；工具接受请求、进程退出或模型最后一句话都不等于业务完成。

哈希证明字节一致，不证明内容正确；HTTP 200 不证明完整业务流程；单元测试不证明真实服务兼容。保留人工修改与草稿，发生冲突时让用户可以恢复，不通过直接覆盖文件绕过编辑协议。

持续改进有停止条件、预算和新材料触发点。达到标准就交付，缺少进展时汇报阻塞，避免为了表现“持续”而无限修改同一成果。

## 10. 先跑通场景，再扩大抽象

先完成个人情境跨任务生效，再做跨事项影响，随后接一个真实来源、一种成果和一个反馈渠道。用真实重复需求决定是否扩展接口，不先建设通用插件市场、知识图谱或分布式平台。

借鉴外部项目时写清：本项目缺什么，对方哪个模块解决它，映射到哪个现有模块，替换/迁移什么，怎样测试。代码移植前固定版本、核对许可证、依赖与平台假设；只借鉴概念也要注明是设计建议，不能写成已接入。

## 11. 数据、兼容与可替换性

模型、来源和通知渠道经现有接口或最小适配器接入，不将业务状态绑定到特定供应商的会话 ID。开发中继与正式连接分开，认证生命周期和故障恢复有独立验收。

格式变化提供版本、兼容读取、迁移和回退策略，不原地改变旧字段含义。不把密钥、个人配置、真实用户数据、机器路径或运行日志提交为源码。开发测试使用隔离目录，不删除真实任务来恢复环境。

健康等敏感信息只在实现所需范围内处理，外部来源和模型只接收必要内容。对建议依据、事实不确定性与执行权限分别表达，避免把一般照顾场景扩张为未经授权的专业决策。

## 12. 对抗性审查与验证分层

每项行为改动先复现或建立失败场景，再审查：重复、乱序、超时、权限撤销、状态过期、暂停、版本冲突、人工修改和重启时会怎样。测试覆盖真实生命周期和可观察结果，不只镜像实现字段；不为通过而放宽断言或清理数据。

按范围执行相关测试与轻量验证；纯文档运行文档和格式检查，行为变更运行相关测试及 `npm run verify`，广泛改动或发行验收再运行 `npm run verify:full`。本地假模型、浏览器渠道、真实模型、真实来源、原生操作与干净安装分别记证据。完整命令以[测试指南](testing-local-run.md)为准。

测试失败保留具体原因，跳过不算通过。历史记录不能自动继承给新版本；重新打开已关闭问题时同时更新阶段状态及剩余风险。界面优先通过布局与清晰操作说明下一步，保留必要标签、可访问名称和不可逆操作后果。

## 13. 决策登记与变更规则

“已确定”指本轮采用的路线；“待设计”表示尚无实施合同；“暂缓”表示有意不进入当前主线。改变决定时说明新证据、影响与替代方案，不因发现另一个项目功能更多而推翻底座。

| 编号 | 决定                                         | 状态与理由                                             | 重新评估条件                                    |
| ---- | -------------------------------------------- | ------------------------------------------------------ | ----------------------------------------------- |
| D1   | 以 CoworkOS 为执行底座，按模块迁入 OnIt 积累 | 已确定；本机准备已有限定范围验收，减少重建通用执行系统 | 真实核心场景出现无法局部解决的底座障碍          |
| D2   | 优先建设个人情境与跨事项协调                 | 已确定；这是已确认定位与现有底座之间的主要差距         | 产品定位发生明确变化                            |
| D3   | 一套运行时管理执行与恢复                     | 已确定；避免重复派工与状态冲突                         | 出现明确远程/多执行器需求，先设计身份和交接合同 |
| D4   | 临时情境与稳定记忆保留不同生命周期           | 方向已确定；存储、权限、失效和事件格式待 M1 设计       | 有数据和兼容证据证明可安全共用部分底层机制      |
| D5   | 首个来源与反馈渠道采用最小适配               | 方向已确定；具体渠道待选择，优先评估已有连接器         | 实际来源能力、授权方式或可靠性不满足场景        |
| D6   | 应用插件化、目录瘦身及界面重写延后           | 暂缓；当前不阻塞核心私人助理链路                       | 实测依赖、安装或扩展成本开始阻塞主线            |
| D7   | 不同时引入其他项目的完整调度器或新框架       | 已确定；先吸收准入、授权、回执和通道规则               | 现有运行时无法满足经验证的新规模或恢复要求      |

新增长期原则记录在本页，并关联决策编号；进度只更新路线。落地的架构、接口、数据布局和支持范围同步其主文档。提交和交付说明写明问题与结果、涉及模块、实际检查、失败/跳过及未验证范围；Git 说明使用中文。
