# Visual evidence and bounded revision

`read_image` supports native-image and configured-vision-model routes. In the fallback route the image-analysis connection selected in model settings sees the pixels and returns textual evidence. A successful report counts as visual inspection; it does not mean the main model saw the pixels. The tool description names the configured model.

Use `review_slides` when a configured vision connection makes it available. Submit every final page in order and the contact sheet as `overview` in the same call. Main defaults to `scope:"project"`, runtime agents to `scope:"work"`; select `scope:"task"` for shared Task previews. Slide and overview paths resolve against that selected input root, accepting relative paths or absolute paths inside it. `reportPath` is separate: it always resolves inside the Agent's own report directory, irrespective of input scope. For Main this is `agents/main/work/` in the Task; runtime agents use their own working directory. Keep the ledger path relative to that directory or absolute inside it, ending in `.json` and away from framework state. The returned `reportScope:"work"` identifies this ledger base; shared Task image access does not grant shared writes.

When using `read_image`, prefer `paths: ["preview/slide-01.png"]`, `review: true` and a concise `goal`. Review one page at a time and omit the unused `path` alias. Prefer paths relative to the selected root: Main defaults to `scope:"project"`, runtime agents to `scope:"work"`; `scope:"task"` reads the shared Task. Absolute paths inside that same selected root are also accepted. Follow the active schema instead of guessing the workspace base.

Example goal: `第3页：检查文字遮挡、溢出、图表单位和可读性。每项给出位置和可执行修改；不超过6项，不全文转录。`

For the contact sheet, ask for design evidence as well as consistency. Example: `检查整套PPT的主题辨识度、主视觉、阅读层级、连续重复版式和留白用途；指出最影响表达的至多3页及具体改法。不要把无溢出等同于设计优秀，也不要为追求变化而建议无关配图。`

For a technical/image-led page, include its intended explanation in the goal, e.g. `本页应说明递归状态如何沿时间传递；检查箭头、标签和结构是否清楚，是否仍主要依赖文字列表。` Review cannot independently authenticate a chart's source: verify values against the material in a separate factual check.

Fallback results include `details.review` with `status` (pass/needs_revision/unreviewed), `summary`, and issues (`severity`, `location`, `problem`, `fix`). `imageHash` (or the hash under `details.images` when using `paths`), `elapsedMs`, `cached`, and model name identify the evidence. General image questions can omit `review` to retain free-form analysis. Native-image results require the main model to record the same review fields after inspecting the returned image.

1. Include the contact sheet as `overview` in the batch so its subject-identity, visual-hierarchy and page-rhythm check runs alongside individual pages instead of blocking them. Identify consequential repetition, unused suitable imagery and empty regions without a compositional purpose. Save deck-level findings alongside per-page evidence. A contact-sheet pass is not proof of readable individual pages.
2. Inspect every final slide at full resolution with one `review_slides` call: `{"slides":[{"path":"preview/slide-01.png","goal":"Explain the page purpose and check legibility and diagram correctness"}],"reportPath":"preview/review.json","overview":{"path":"preview/contact-sheet.png"},"concurrency":2}`. List every final PNG in page order, including unchanged pages on later calls. The tool queues the next page whenever a worker finishes, persists results and attempt counts, and reuses checks matching the exact image hash and stable goal. Default to two workers; use up to four only with known provider capacity. If unavailable, use `read_image(review: true)` for every page in the appropriate scope with the same concurrency bound.
3. Keep the task-local `review.json` written by the batch tool: per-page path, image hash, model, actual status/issues, and attempt history. Reuse this same ledger; do not fabricate or replace its checks. Keep your repair actions in a separate file. Never mark failed or absent responses as pass.
4. Read the complete batch, triage findings, and fix concrete visible defects and consequential design weaknesses together in one source edit. Do not rebuild after each individual page review. Keep design findings distinct from clipping, missing content and factual defects; a technically readable deck may still need a better composition or explanatory diagram. Record which findings were fixed or retained with a reason. Do not change facts merely because a vision model guessed a different value.
5. Rebuild and re-render once per consolidated repair, then submit all final PNGs to the same batch ledger with unchanged goals. Only changed image+goal pairs require new remote checks, including across restarts. Associate the final report with the final image hashes, not the earlier render.
6. Allow at most one retry per failed check. Default to one consolidated repair round; allow one further round only for a remaining major defect. If unresolved, deliver with the specific incomplete checks/issues clearly identified, rather than claiming the deck passed. A second round is justified by a remaining defect, not simply by a desire for another opinion.

`review_slides` saves a task-local ledger, deduplicates equal image+goal pairs in a batch and keeps retry counts across restarts. Its pass flag covers submitted pages only; Main must verify that every final deck page is represented. `read_image` separately caches successful evidence per tool session and shares identical in-flight requests within a cancellation scope. Two identical failures stop retries; cancellation is forwarded to requests and is not passing evidence. Neither mechanism is a provider-wide billing quota or a guarantee that remote computation stopped. Do not bypass retry limits by changing the wording of a goal.

Before visual review, run deterministic checks. `validate_slides.mjs` now reports broken package references, invalid XML, object bounds, text-box overlap, estimated text fit and font availability. Warnings require inspection; the estimates do not prove clipping. Grouped/rotated objects and differences between LibreOffice and PowerPoint still require visual verification.
