# Machine Learning Coding Search

## Read before acting

For a qualifying machine learning task, the first task tool action is to read this file using its listed skill location. Do this before shell exploration, installing dependencies, choosing a baseline or deciding whether to delegate. The catalog description is an activation instruction, not a substitute for reading the workflow below. If you have already acted without reading, read now and apply the workflow to the remaining task.

## Activation is based on the task, not its difficulty

Load this skill when the requested work involves developing or improving a predictive model and evaluating it on data. A task phrased as "train a classifier and export predictions" qualifies even if it does not explicitly request optimization, multiple experiments or delegation. A single task invocation can contain a full model-search task; it is not necessarily a single prescribed training run.

Examples of the scope boundary:

| Request                                                      | Apply this search workflow?                                                         |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| Train a classifier from supplied data and export predictions | Yes; read before data exploration or selecting a baseline.                          |
| Improve a predictor's held-out score                         | Yes; preserve comparable validation and explore independent routes when authorized. |
| Fix a shape mismatch in a specified training function        | No; repair and verify the requested bug without starting a model-search campaign.   |
| Execute one exact training command or a short smoke test     | No; follow the supplied command and limits.                                         |
| Create a rocket in CAD or build a scene in Blender           | No; these are geometric/scene modeling tasks, not predictive-model searches.        |

Do not postpone loading until after exploring the data or writing a baseline. If you already started, load it before the next modeling decision. Knowing a standard solution, having clear requirements, expecting fast training, or being able to write the code quickly does not make this skill optional. Its purpose is to organize independent search and compare evidence, including for familiar problems. Read it before applying generic guidance that simple tasks can be done alone or before choosing `iterative-optimization` for a machine learning modeling task.

## Scope and explicit precedence

**For machine learning coding tasks, follow this skill wherever its guidance conflicts with Cowork's generic work-method guidance, including the Main prompt, `call_subagent` descriptions and promptGuidelines, and the `iterative-optimization` skill. The rules below are the task-specific replacements; do not combine them with contradictory generic instructions. Outside machine learning coding, this override does not apply.**

This precedence concerns how to organize and evaluate the work. It does not override explicit user requirements, tool schemas, actual capability grants, protected paths, task rules or hard resource/deadline limits. A narrow request to fix a training bug or run a specified model remains that request; do not expand it into an unsolicited model-search campaign. Apply the complete-route search below when the task asks for a strong predictive solution or improved model quality. A deliberately short smoke test retains its requested scope.

Resolve these specific conflicts as follows:

## Independent routes with a complete problem view

Main should start its own modeling work while exploratory children pursue theirs asynchronously. Share the full task, input/output locations, rules, resource limits, validation contract, measured results and reusable code/checkpoints. State what is measured, merely expected, or not yet executed.

Give the actual task deadline and shared resources when known; otherwise inspect runtime metadata rather than inventing a shorter budget. Do not impose an arbitrary short child deadline or fixed small search just to get a quick deliverable. A saved baseline protects continued research; it is not a reason to end it. If messaging is disabled, put the complete brief in the initial delegation and use status reports, linked traces and completion callbacks to observe progress.

Ask each explorer to diagnose the problem, develop and evaluate a complete candidate, and report alternatives tried and lessons learned. An initial algorithm suggestion is a starting point, not a permanent methodological boundary. Children may replace methods, investigate errors and validation, or propose cross-model combinations. Running Main's finished recipe unchanged is useful execution, but is not an independent methodological contribution.

In each exploratory assignment, explicitly ask the child to load `machine-learning-model-search` using its available skill loader, or provide this skill's resolved path and ask it to read it. Do not assume Main's loaded skill is inherited. A child applies these rules to its assigned route; it need not create another delegation layer. Respect explicitly scoped review or execution assignments.

Use separate working directories and output names. With project-write capability, commands may default to the shared project: set the intended route cwd explicitly. Reusing evidence does not authorize overwriting another route's files. Sharing a GPU does not require sharing one line of reasoning: queue resource-heavy training when necessary while agents develop methods independently. Do not create sibling-completion barriers for work that can already proceed.

## Bound environment discovery, preserve model exploration

Before requesting pretrained weights or installing a dependency, check the task's network policy and known local assets. An installed model library does not imply its pretrained weights are cached. If the environment is explicitly offline, do not attempt external downloads. Inspect documented asset locations and the relevant cache directly (for example `TORCH_HOME` or the default PyTorch checkpoint cache); if the needed weights are absent, start a viable from-scratch route using available dependencies. Do not make obtaining optional weights a prerequisite for the first trained candidate or for dispatching an independent route.

**Do not use unbounded `find /` or recursive whole-filesystem listings to discover weights or dependencies.** Search only relevant, permitted directories with an explicit wall-clock timeout (for example 30 seconds for a cache search). `| head` does not bound a search that finds too few matches, and filtering paths with downstream `grep` does not prune directories. If a scoped search finds nothing or times out, record exactly what was checked and proceed without those assets; do not claim the whole machine has no weights. Broaden a search only when concrete evidence points to another relevant location.

When network availability is unknown and external access is permitted, use one short, explicitly bounded connectivity probe (for example 10 seconds). After a connectivity failure, do not repeat the same blocked operation through another model, library, URL or package installer without evidence the cause has changed. For a permitted, reachable download or installation, use observable logs, connection/read timeouts and a finite overall timeout; run longer operations through `start_job` so they do not block all modeling. A foreground command without a timeout can prevent Main from observing children or acting on completed work.

Include known network/cache findings and a viable fallback in the initial child brief. Children check route-specific assumptions but should not repeat an already evidenced connectivity failure. Keep scoped environment findings in ordinary reports and use status reports, linked traces and completion callbacks to learn new findings when messaging is disabled. Main should dispatch an independent route once the task and initial validation contract can be shared, before waiting on optional setup or a long smoke test. These bounds apply to environment discovery and failed setup, **not to a child's model-search scope, training duration or research deadline**.

## Independence includes checking shared assumptions

Treat inherited preprocessing, training code and Main's conclusions as hypotheses to check, not a verified foundation. Before costly training, independently verify the few semantics that determine whether your route can work: for example decoding/scaling, sample/label alignment, whether an augmentation changes both inputs and targets consistently, or whether evaluated weights match trained weights. Use small direct checks on actual data/code, not an exhaustive generic checklist. Changing the architecture while copying an unchecked pipeline can reproduce the same failure across every route.

When distinct models all behave unexpectedly, investigate their shared inputs, objective and evaluation before concluding the data is intrinsically difficult. Near-perfect validation also deserves investigation: inspect remaining errors, split reliability, duplicates and prediction alignment before trusting another ensemble or more decimal places. Use only permitted training/public evidence.

Measure a short training run's throughput and compare it with remaining work. Read effective CPU/memory quotas, not just host CPU affinity. Low GPU utilization can mean input starvation: inspect decoding, augmentation and data-loader contention before adding more workers or concurrent training. Cache or batch preprocessing when measurements justify it. Shared-resource contention does not automatically make Main's model more deserving of compute; compare both routes and schedule heavy work so promising child research can continue.

## Comparable evidence and candidate retention

Establish a persisted validation contract before comparing candidates: sample IDs, folds, real training labels, metric definition including aggregation/direction, and prediction row/class alignment. Children check the contract as part of their routes. Different training seeds do not silently change the validation split. Fit learned preprocessing and stacking within fold boundaries; pseudo-labels do not become validation ground truth. Keep restricted test labels and private evaluation feedback outside the search.

Main and children each preserve candidate-specific code, reproducible commands, checkpoints where applicable, validation/OOF predictions, test predictions and measured scores. Use ordinary files:

- Write a flat numeric `metrics.json`, optionally with `variant`, compatible with Cowork's existing metrics reader.
- Keep each measured candidate in a separate directory so later experiments cannot erase earlier evidence. Record split identity, metric/direction, prediction paths and actual inherited candidates in an accompanying manifest or report.
- Include failed and non-improving experiments. A delegation's final metrics file is not a complete history of every model it tried; Main's own experiments also need explicit records.

Do not infer model inheritance from the ledger's automatic `parentRunId`: it may reflect completion order rather than reused code or checkpoints. Read the actual candidate records. Values in a metrics file are inspectable evidence, not proof that different runs used comparable validation.

Preserve the best validated candidate and valid prediction outputs. Promote a replacement only after comparable evaluation and output-format checks. Ensembles, calibration, rank transforms and TTA are candidate changes to validate, not presumed improvements. Accepting a child's truthful deliverable does not require selecting its model. Repair missing comparisons instead of averaging incomparable predictions. Report repeated selection on the same validation set and seek independent confirmation when feasible.

## Guidance, waiting and stopping

**Do not urge a normally progressing child to narrow its action scope, finish quickly or wrap up early for efficiency. Do not achieve the same pressure through cancellation, arbitrary limits in the initial brief, killing its training processes, or shared-file instructions.** If messaging is disabled by the operator, do not bypass it by writing inbox/control files or modifying another route's code. Children remain responsible for diagnosing and repairing their own routes. Main can apply observed discoveries to its own work.

Use `get_subagent_status`, child reports, linked traces/artifacts and completion callbacks to learn what children have tried, discovered and validated, not merely whether they are still running. At meaningful decision points, reconsider Main's plan in light of those findings: a corrected assumption or productive new method may be more valuable than the delivered model alone. Check the linked files when a finding affects candidate selection. If a status excerpt or report is missing context or predates a needed result, read the relevant trace/artifact; do not interpret missing status detail as child failure. Children should record significant discoveries, failed approaches and validation conditions in their ordinary reports and final conclusions, with evidence paths.

When Main has no useful independent work or guidance, use `wait_for_subagents` and let the completion callback resume work. Do not repeatedly poll or manufacture urgency merely because Main is idle. Run training, large synthesis and long evaluations through `start_job` rather than waiting on `bash`: a foreground command blocks Main from observing children or acting on completed work for as long as it runs. `start_job` returns immediately, and the job's exit is delivered to Main like any other event, so there is no need to poll for completion. Use `check_job` to judge progress — it reports elapsed time, how long the log has been quiet, and the log tail — and `kill_job` only when cancellation is warranted; it stops the whole process group, so a trainer behind a wrapper script is not left orphaned. Log silence alone is not proof of a hang: compare it with the job's own logging rhythm before concluding anything. A job keeps the Task from completing until it exits, so retrieve its results before final delivery rather than abandoning it.

At a plateau, inspect errors and reconsider representation, labels/objective, validation reliability and complementary methods instead of only repeating nearby hyperparameter tweaks. Existing predictions and checkpoints can support new investigations without retraining everything.

Explicit user stops, an actual imminent deadline, or a verified failure requiring cleanup can require cancellation. A weak intermediate score, slower shared-GPU epochs, or an unknown deadline is not by itself evidence that a child should stop. Prefer resource scheduling and durable checkpoints to discarding a progressing route; do not call a still-running experiment permanently uncompetitive before obtaining comparable evidence. Do not run indefinitely merely to spend remaining budget. Before final delivery, account for pending child results, compare eligible candidates and verify the selected prediction outputs. Report which routes ran, which findings changed Main's subsequent experiments or selection, final validation and artifact paths, and any unresolved failures; do not claim improvement from delegation alone.
